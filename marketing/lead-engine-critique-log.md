# Adversarial review logs (compliance + feasibility)

## Critique A — Compliance & Risk

# COMPLIANCE & RISK REVIEW — Adversarial Findings (15 fixes, severity-ordered)

Repo facts verified before review: `cms/hooks/deny-hermes-publish.ts` exists and is wired into articles/news-items/pages/projects; `HERMES_AUTO_PUBLISH_CATEGORIES` lives in `app/api/hermes/ingest/route.ts`; the WhatsApp presence is `components/layout/whatsapp-fab.tsx` — a click-to-chat FAB, **inbound only, no outbound send capability anywhere in the repo**.

---

1. **[orchestration vs automation vs compliance — CRITICAL] Three conflicting auto-publish paths; Subsystem 5's forges owner intent.** Subsystem 5 has n8n auto-publishing every 15 min "via signed token to `/api/automation/approve`" — that mints the *owner's* approval credential for a cron job, so an auto-publish is indistinguishable from a human approval in the audit trail (and bypasses Subsystem 6's claim-diff guard and Subsystem 2's five conditions entirely). Fix: delete Subsystem 5's sweep. Exactly ONE publish path: Subsystem 2's hourly sweep → Subsystem 6's `POST /api/publish/guard`, authenticated by its own secret (not the approval JWT, not `HERMES_AGENT_SECRET`), writing audit action `auto-published-24h` — never `approved-by-owner`.

2. **[automation vs compliance — CRITICAL] The 24h timer can start on email that was never delivered.** Subsystem 2 sends approval mail via a plain SMTP node (Zoho/Google mailbox). Plain SMTP emits no delivery webhooks, so Subsystem 6's R7 mitigation ("clock starts only on provider `delivered` event") is **unimplementable as designed** — silence-from-spam-folder becomes "approval." Fix: approval emails MUST go through a webhook-capable provider (Resend, already named in Subsystem 5 Phase 0); guard endpoint refuses to start `pendingSince` until a `delivered` event is recorded in `publish-audit`; no event within 6 h → item locks to manual queue and an alternate-channel alert fires.

3. **[automation — CRITICAL] `market-insight` is in the auto-publish whitelist.** Subsystem 2's `REVISION_AUTO_PUBLISH_CATEGORIES` includes `market-insight` — a category that is numbers by definition (tariffs, prices, MW figures), directly contradicting Subsystem 1 editorial rule 7 and Subsystem 6's whitelist (`industry-news-roundup, knowledge-explainer, glossary`). Two different whitelists means the looser one wins operationally. Fix: one env var, Subsystem 6's list verbatim, `market-insight` removed; document for the owner that this deliberately narrows his "auto-publish everything after 24h" requirement (get sign-off so nobody "fixes" it later by widening the list); ship `AUTO_PUBLISH_ENABLED=false` until claim-diff guard has run in shadow mode ≥2 weeks.

4. **[leadgen — HIGH] Calculators use marketing ceilings as math inputs = misleading personalized projections.** `diesel-vs-bess` computes "annual BESS cost using catalog figures (≤75% saving cap, 95% RTE)". Feeding "up to 75%" — a hedged marketing claim — into a user-specific calculation converts it into an individualized savings promise, and outputting "BESS cost" collides with the standing "never quote prices" rule the chatbot already enforces. Fix: calculators compute only from user inputs + cited `tariff-rates` global data; the 75% figure never enters the formula; outputs labeled "indicative estimate — not a quote or guarantee" rendered server-side; result ranges, not point values, for anything cost-related.

5. **[tracking vs leadgen — HIGH] Pre-consent server-side tracking is not actually anonymous.** Subsystem 4 claims server events "carry no cookies and no PII → run regardless of banner state," yet A2 parses the `ph_*` PostHog cookie for `distinct_id` and attaches `lead_id` — that is pseudonymous profiling linked to an identifiable person, pre-consent, contradicting both the banner and Subsystem 3's "cookieless until consent" model (the two subsystems also specify different consent architectures). Fix: one consent model; pre-consent server events use per-request random UUIDs, no `ph_*` cookie parsing, no `lead_id`; the lead-joined variant fires only after consent cookie is present.

6. **[automation + compliance — HIGH] Outbound WhatsApp is invented infrastructure.** Subsystem 2's alert fallback and Subsystem 6's T+12h reminder both "send WhatsApp messages" — but `components/layout/whatsapp-fab.tsx` is an inbound click-to-chat link; outbound requires a WhatsApp Business API account that does not exist. Same defect: Subsystem 6's "owner can reply `HOLD <id>`" requires inbound-mail parsing that nothing provisions. Fix: strip WhatsApp and reply-parsing from all alert/approval flows; alerts = email + `/admin` queue. If WABA is wanted, add it to Subsystem 5 Phase 0 blocking inputs explicitly.

7. **[content vs compliance — HIGH] Quoting limit contradiction: 75 words vs 15 words.** Subsystem 1 editorial rule 4 permits ≤75 verbatim words from news sources; Subsystem 6's lint blocks >15. Only the linted rule exists in practice — but the documented 75-word rule is what writers/Hermes will follow, and 75 verbatim words from Daily Star/Prothom Alo is real copyright exposure under Bangladesh's Copyright Act 2023 fair-dealing limits. Fix: one number (keep the 15-word lint), amend Subsystem 1 rule 4 to match, and run `content-lint.ts` at Hermes ingest time, not only in the nightly pipeline — otherwise human-authored drafts skip the gate.

8. **[content vs compliance — HIGH] Third-party brand naming is simultaneously planned and banned.** Subsystem 1 schedules "H&M/Inditex supplier decarbonisation deadlines"; Subsystem 6 rule 3 bans naming any entity not in `clients` with `publishApproved: true`. As written the rule blocks legitimate buyer-requirement reporting, so it will be ignored — and then nothing governs statements about named multinationals (misstatement/defamation risk, plus Cyber Security Act 2023 defamation exposure in BD). Fix: split the rule — (a) clients/testimonials require written clearance; (b) third parties in news context allowed only with tier-1/2 or the brand's own published source, neutral attribution ("according to…"), no relationship implication, and **always human-approved, never in the auto-publish path**.

9. **[leadgen — HIGH] "Bangladesh Bank uptime guidance" is an unverified citation baked into a deliverable.** The "BESS for Banks & ATM networks" whitepaper cites a BB document that may not exist under that name (the real instrument is the BB Guideline on ICT Security, which covers availability/DR). Planning content around an assumed citation is exactly the invented-source failure the whole system exists to prevent. Fix: gated assets go through the identical claims-gate as articles; every planned citation in Subsystem 1/3's content maps must be resolved to a real document number + date in the `sources` registry *before* drafting is queued.

10. **[automation + leadgen — MEDIUM] n8n credential blast radius: Hermes bearer + write-capable Payload key.** Subsystem 2 hands n8n `HERMES_AGENT_SECRET` (revisions masquerade as Hermes in any audit) and Subsystem 3 gives n8n a Payload API key with `leads` update access (a compromise of n8n = write access to the PII store), while Subsystem 4 separately issues a read-only `reporter` key. Fix: n8n gets its own bearer per surface — rename `/api/hermes/revise` to `/api/pipeline/revise` under a pipeline secret; replace the generic Payload write key with a narrow signed-token route `POST /api/leads/confirm?token=` (HMAC, single field flip); keep `reporter` strictly read-only; never reuse `CRON_SECRET` for anything that can publish (it sits in a VPS crontab line readable by anyone on the box).

11. **[all — MEDIUM] Schema fragmentation makes the gates fictional.** `sources` is defined three incompatible ways (S1 `trustTier 1/2/3`, S2 `tier primary/secondary/tertiary`, S6 `tier1-gov/...`), `citations` twice (S1 `quotedClaim/locator` vs S2 `claim/anchorUrl`), `leads` twice (S3 vs S4 — different fields, different upsert logic), and S6 adds a third overlapping `claims[]` ledger. Hooks like `claims-gate.ts` will reference fields that don't exist → validation silently never fires. Fix: declare one canonical owner per collection (suggest: S6 owns `sources`+`claims`, S4 owns `leads`, S1 owns `citations`), merge fields once, and add a Vitest suite asserting every hook/lint field path exists in the generated `payload-types.ts`.

12. **[automation — MEDIUM] Robots/ToS compliance is a table footnote, not a node.** Subsystem 2's n8n chain fetches Daily Star/Prothom Alo/TBS/FE nightly with no robots.txt check step; "respect robots.txt" appears only in the failure-modes table. Newspaper ToS commonly prohibit automated retrieval. Fix: add an explicit robots-check node honoring Subsystem 6's `fetchPolicy` field before every fetch; declared UA (`SustechContentBot/1.0; +https://www.sustechltd.com/llms.txt`); prefer RSS endpoints for all four newspapers; disallowed sources flip to `manual-only` automatically and are never re-fetched.

13. **[automation vs compliance — MEDIUM] Two incompatible approval-token specs.** S2: JWT HS256, `APPROVAL_JWT_SECRET`, 168 h TTL; S6: HMAC, `APPROVAL_TOKEN_SECRET`, 72 h, version-pinned. A 7-day approval link is pointless when the auto-publish timer is 24 h — it only widens the replay/leak window. Fix: one spec — S6's (72 h, version-pinned, single-use `jti`, GET-renders-confirm/POST-acts), one secret name, documented once in `.env.example`.

14. **[compliance — MEDIUM] `sources` registry must not be publicly readable.** Subsystem 6 sets `read: public` (S1 says admin-only — another conflict). Public REST read exposes crawl targets, content hashes, failure counts, and `paywalled` flags — an external map of your scraping behavior, and nothing on the site needs it (citations render server-side from the article document). Fix: `read: isAdminOrEditor` everywhere.

15. **[content — LOW] Company stats typed into cornerstone copy violate the design's own rule.** Subsystem 1 embeds "103+ projects, 8 years" in `/solutions/epc-partner-bangladesh` page copy while its rule 2 mandates these come only from the CMS stats global / `lib/company-facts.ts`. Hardcoded copies drift the day the numbers change. Fix: stats interpolated at render from the global; add a `content-lint.ts` pattern flagging literal `103+|175+|10 sectors|8 years` typed in any body field.

## Critique B — Feasibility

# FEASIBILITY REVIEW — 15 Corrections

1. **Schema split-brain: three incompatible `sources` collections, three `citations` shapes, two `leads` collections.** S1 (`trustTier` 1/2/3, freq daily→quarterly), S2 (`tier` primary/secondary/tertiary, freq nightly/weekly only — can't even hold S1's 26-source seed list, plus `contentSelector`/`etag`), and S6 (`tier1-gov`/`tier2-press`, `paywalled`, `fetchPolicy`) all claim `cms/collections/sources.ts`. Same for `citations` (S1: `quotedClaim`/`locator`/`accessedDate` vs S2: `claim`/`anchorUrl`/`lastVerifiedAt`) and `leads` (S3 vs S4-B1: different source enums, consent groups, and scoring tables — S3 gives calculators +30/report +20/asset +25; S4 gives RFQ +40/calc +30/magnet +15). **Fix:** one canonical schema doc before any code — S2's sources fields (operationally complete) + S6's `paywalled`/`fetchPolicy` + S1's four-level `checkFrequency`; S4's leads upsert model + S3's double-opt-in consent group; one scoring table.

2. **Email-provider contradiction blocks Phase 0.** S2/S3/S4 mandate "no email SDK in web tier, n8n SMTP only"; S5 Phase 1 builds `lib/email/` with a Resend client in the repo. Worse, S6's mitigation 4 ("24h clock starts only on the provider `delivered` webhook") is **infeasible with an SMTP node** — plain SMTP has no delivery events. **Fix:** Resend account, called from n8n via HTTP node (keeps the no-SDK posture, provides delivery webhooks). Delete `lib/email/` from S5 Phase 1. If owner picks bare SMTP instead, drop the delivered-event rule and start the clock at send time.

3. **The combined guards make the user's 24h auto-publish requirement a dead code path — say so explicitly.** S2 ships `AUTO_PUBLISH_ENABLED=false` and vetoes anything matching `৳|%|price|tariff|...`; S6's claim-diff guard blocks any numeric change. The nightly pipeline exists to update tariffs and numbers — so nothing it drafts will ever auto-publish. Probably correct, but it contradicts requirement (4) as the owner stated it. **Fix:** get written owner sign-off in Phase 0 that auto-publish covers only prose-level edits in whitelisted categories; otherwise you're building sweep/timer/guard machinery (~4 dev-days) for a path that never fires.

4. **Invented infrastructure: outbound WhatsApp and reply-by-email.** S2 and S6 send WhatsApp alerts/T+12h reminders "via existing widget infra" — the repo's widget is `components/layout/whatsapp-fab.tsx`, an inbound click-to-chat link. Outbound WhatsApp = Meta Business Cloud API onboarding + number + approved message templates (a separate project). S6's "owner replies `HOLD <id>`" requires inbound mail parsing (IMAP polling) that nothing provisions. **Fix:** v1 alert channels = email + `/admin` queue, full stop.

5. **Cut S6's heaviest gates for v1: the numeric tokenizer, the LLM-judge, Bangla numeric-parity lint, and the JSONL audit mirror.** "Every number must trace" via Lexical tokenization will false-positive on kVA ratings, model numbers, phone numbers, addresses and block legitimate saves; it also duplicates S1's simpler `CITATION_REQUIRED_CATEGORIES` publish hook — two enforcement points for one rule. The LLM-judge adds an Anthropic dependency to every nightly run for marginal value, and `/var/log/sustech/publish-audit.jsonl` duplicates an append-only Payload collection. **Keep for v1:** S1's category hook, S6's banned-phrase lint list (cheap regex), `claims[]` as a *data* field, `publish-audit` collection only.

6. **Version retention is triple-specified and mis-modeled.** S2 wants weekly Sunday prune, S5 monthly 1st 05:00, S6 monthly-with-audit-exceptions — pick one or zero. Reality check: `articles.ts:23` has `autosave: { interval: 375 }`, so version churn is dominated by autosave, not "~90 nightly revisions"; and Payload 3's Local API exposes `findVersions` but no public `deleteVersions` — pruning means dropping to the adapter (`payload.db.deleteVersions`). **Fix:** raise `maxPerDoc` to ~50 (Payload auto-prunes by count) and skip the prune job entirely in v1; the 3-month requirement is satisfied by count-based retention plus the audit log.

7. **Approval flow has two secrets, two TTLs, three route shapes, two sweep cadences — and S5's sweep design is wrong.** S2: `APPROVAL_JWT_SECRET`/168h/`/api/approve?token=`/hourly sweep. S6: `APPROVAL_TOKEN_SECRET`/72h/`/api/approve/[token]` + `/api/publish/guard`. S5: `*/15 * * * *` sweep "via signed token to `/api/automation/approve`" — incorrect: approval tokens are per-email, single-use artifacts; the sweep must auth with `CRON_SECRET` to a dedicated sweep endpoint (S2 got this right). **Fix:** adopt S2's design wholesale, fold in S6's version-pinning check, one secret name, hourly cadence.

8. **S3 asserts "Subsystem 2's nightly job updates the `tariff-rates` global" — S2 never writes tariff data, and must not.** S2 is drafts-only by design; a cron silently mutating live calculator rates is exactly the R2 failure S6 enumerates, and Payload **globals have no drafts**, so an auto-write would bypass every approval gate in the system. **Fix:** watcher flags the tariff source change in the daily email → owner updates the global manually in `/admin` → revalidate hook refreshes calculators.

9. **Analytics consent contradiction + event-name drift.** S3: cookieless `persistence: "memory"`, no banner. S4: consent banner, `st_consent` cookie, init-on-accept. Also S3 names `calc_completed`, S4 `calculator_completed`; S3 fires `rfq_submitted` client-side, S4 server-side. **Fix:** take S3's cookieless mode for v1 (no banner debt), take S4's typed `lib/analytics/events.ts` as the single event registry and server-side conversion capture; delete the banner from scope until cookies are actually needed.

10. **The Payload custom admin "insights" view (S4-D) is v2.** Custom views need `admin.components.views` wiring, importMap registration, and a bespoke chart component — several dev-days replicating data the owner already gets from the daily email, the `daily-reports` list view, and `leads` with `defaultColumns`. Build it only if the owner asks after a month of using the email reports.

11. **Defer pre-revenue polish: exit-intent nudges (S3-d), `short-links`/QR (S4-E), newsletter double-opt-in workflows + `email-suppressions` (S6).** There is no newsletter to suppress yet, and popups optimize traffic a noindex beta site doesn't have. **Keep the consent schema fields on `leads` from day one** (cheap now, painful to retrofit); defer the n8n confirm/suppression/unsubscribe workflows until the first nurture email is actually planned.

12. **S5's phase order builds automation before there is anything to automate.** Phase 3 (nightly watcher) before Phase 4 (calculators/tariff-rates), yet the watcher is useless until articles carry citations and the tariff global exists; Phase 2's "10 cornerstone articles in 3–4 weeks" silently depends on Phase-0 items 8–9 (cleared client assets, Manus dossiers) that have no owner deadline. **Fix:** 0 → 1 → 2a (sources + citations schema only, ~3 days) → 4 (calculators + tariff-rates) → 2b (content cadence, continuous) → 3 (watcher, once ≥10 cited articles exist) → 5 → 6.

13. **Effort is ~2x understated.** S5's 30–40 dev-days excludes S6 entirely (content-lint, publish-audit, guard endpoint, three Vitest suites ≈ 8–10 days), S3's five blocks + three calculators + nudges (≈ 10–12 days), S4's dashboard, and n8n workflow build/test time (6+ workflows needing staged runs against beta ≈ 5 days). Everything as written ≈ 60–75 dev-days. With cuts 4, 5, 6, 10, 11 applied, 35–40 becomes honest.

14. **The VPS fallback cron has no owner and no liveness check.** S2 specifies the crontab line, S5's RACI gives Hermes "VPS ops", but no phase deliverable installs or documents it, and a crontab that silently dies defeats its purpose (it only fires when n8n is *also* dead — double-silent failure). **Fix:** Phase 3 deliverable = crontab entry documented in `DEPLOYMENT-AND-VPS.md`, installed by Hermes, plus a weekly forced heartbeat run whose timestamp appears in the daily report ("fallback cron last seen: {date}").

15. **Payload 3 implementation gotchas glossed over.** (a) `where[citations.source][equals]` into an array-of-relationship works but needs `index: true` on the relationship or the nightly affected-docs query degrades as content grows; (b) "on reject, restore latest published version" — Payload has no one-call discard-draft; you must `restoreVersion` or re-`update` with published data — build the helper once in `lib/versions.ts`; (c) the approve route's `payload.update({ _status: "published" })` passes through the existing `denyHermesPublish` beforeChange hook (`cms/hooks/deny-hermes-publish.ts`) — it must execute under its own internal identity (per S6 §6d.4), never the Hermes service account, or the deny hook blocks the publish and the audit log misattributes the actor.
